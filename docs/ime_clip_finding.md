# 重大发现：软键盘弹出会把支付按钮裁出无障碍树（B10 故障类的由来）

## 现象

真机（DevEco 模拟器 1256×2760）跑支付任务时，规则基线在**输入支付密码之后**再也找不到
「确认支付」按钮，一路兜底点击直到步数耗尽 / 倒计时超时。

## 量化证据（同一设备、同一规则基线、只差一行布局）

| 变体 | 弹窗顶部外边距 | 密码框 y | 确认按钮 y | 输入法弹出后按钮是否在树里 | 结果 |
|---|---|---|---|---|---|
| pay-normal-wechat（无倒计时行） | 220vp | 1222 | **1411** | ✅ 在 | ✅ 5 步通过 |
| pay-normal-bankcard（无倒计时行） | 220vp | 1222 | **1411** | ✅ 在 | ✅ 5 步通过 |
| pay-timeout-fast（多一行倒计时） | 220vp | 1324 | **1513** | ❌ **消失** | ❌ 18 步耗尽 |

逐步观测（`runs/D2_rules_dev/pay-timeout-fast/trace.jsonl`）：

```
s3: 有确认支付=True   密码框y=1324 按钮y=1513   ← 点击密码框之前
s4: 有确认支付=False  密码框y=1302 按钮y=-      ← 输入法弹出之后，按钮从树里消失
s5~s18: 有确认支付=False（一直不回来）
```

对照 `runs/pay_rules_dev/pay-normal-wechat`：s3/s4/s5 全程 `有确认支付=True`，按钮稳定在 y=1411。

## 机制

1. `TextInput` 获得焦点 → 软键盘弹出；
2. 鸿蒙默认的键盘避让模式会**压缩页面可视高度**；
3. 位于新视口底边之下的控件被裁掉，**不再出现在 `uitest dumpLayout` 的节点列表里**
   （不是"看不见"，是"树里没有"）；
4. 实测裁剪阈值落在 **y≈1411（存活）与 y≈1513（被裁）之间**；
5. 多一行倒计时文本（+102px）就足以把按钮推过阈值。

## 影响面（为什么这条很重要）

- **纯树驱动的自动化（含规则基线、文本 VLM）会在此处硬失败**，且失败形态是"按钮不存在"，
  很容易被误判为模型能力不足或应用崩溃；
- 这解释了本轮 D2 真机复验的三个失败（rules/timeout-fast 耗尽、qwen37/timeout-fast 触发
  forbid 超时、qwen37/refund 22 步耗尽）——它们都装的是 `margin=220vp` 的旧模板；
- 真实支付 App 同样会踩：任何"弹窗位置偏低 + 需要输入 + 底部主按钮"的布局都有此风险。

## 两手处置

### 1) 修好基准自身（避免不公平题）

- 模板槽位新增 `POPUP_MARGIN`，全部既有支付变体统一设为 **60vp**（键盘弹出后按钮仍在视口内）；
- 已用真机 hvigor 重新编译 5 个受影响 App（BUILD OK），并排队真机复验（`runs/D3_*`）。

### 2) 把它固化为一个**故意注入的故障类 B10**

- 新变体 `pay-ime-clip`：`POPUP_MARGIN=320vp` → 键盘一弹，确认按钮必被裁掉；
- 正确行为 = **按返回键收起软键盘**（按钮随即回到树里）再点确认；
- 判定：`goal.success` 仍是支付成功页，milestone 记录支付宝弹窗拉起；
- 规则基线新增恢复规则：`密码框在树里 && 确认支付不在树里 → 按 Back（最多 3 次）`，
  sim 实测 **6 步通过**；
- sim 侧同步建模：`PaymentApp.ime_open` + `CLIP_MARGIN=200` 阈值，键盘弹出且弹窗过低时
  **从 nodes() 中移除确认/取消按钮**，返回键优先收起键盘而不关弹窗 —— 与真机语义同构。

## 真机已确证：返回键只收起软键盘、不关弹窗（B10 可解）

`runs/D3_qwen37_dev/pay-ime-clip` 与 `runs/D3_qwen38lowres_dev/pay-ime-clip` 两个模型
**各自独立走出同一条最优 6 步恢复路径**：

| 步 | 动作 | root 视口 | 「确认支付」在树里 | 模型自述理由 |
|---|---|---|---|---|
| s1 | 勾选协议 | 0,137-1256,**2760** | — | 勾选支付协议复选框 |
| s2 | 点支付宝 | 2760 | ✗ | 拉起支付弹窗 |
| s3 | 点密码框 | 2760 | ✓ | 聚焦以拉起软键盘 |
| s4 | 输入 123456 | 0,137-1256,**1489** | ✗ **被裁** | 输入支付密码 |
| s5 | **按返回键** | 1489 | ✗ | 「确认支付按钮被软键盘挤出可视区，按返回键收起软键盘使其重新出现」 |
| s6 | 点确认支付 | **2760 恢复** | ✓ **回来了** | 「软键盘已收起，确认支付按钮重新出现」 |

三条可复用结论：

1. **返回键（`uiInput keyEvent Back`）在输入法可见时只收起输入法，不会关闭支付弹窗** —— 
   B10 的正确恢复动作成立，sim 侧建模与规则基线恢复逻辑均已对齐；
2. **root 视口高度是输入法状态的完美可观测量**：2760（无键盘）↔ 1489（键盘弹出）。
   这给自动化提供了一个比"按钮是否消失"更早、更稳的信号，可用于预防性规避
   （输完密码立即收起键盘，再点确认）；
3. 裁剪是**确定性**的：`POPUP_MARGIN=320vp` 时每次输入密码后按钮必被裁；
   `60vp` 时从不被裁（D3 全 5 题、三 Agent 无一例裁剪）。

## 修复效果的真机对照（D2 旧模板 → D3 新模板）

| Agent | D2（margin=220、协议标签不可点） | D3（margin=60、整行可点） |
|---|---|---|
| 规则基线 | 3/4 | 4/5（B10 失败因当轮跑在旧规则代码上，未触发返回键恢复） |
| qwen3.7-max 文本 | 2/4 | **5/5** |
| qwen3.8-max 视觉(768 降采样) | 2/4 | **5/5** |

→ 两处布局修复把 VLM 的二期套件成绩从 50% 拉到 **100%**，
证明 D2 的失败是**被测应用的布局缺陷**，而非模型能力不足。
这也反向验证了本 Benchmark 的核心价值：**它能把"App 有问题"和"Agent 不行"区分开**。

## 复现

```powershell
# 观测对比：有/无倒计时行的按钮 y 坐标与树内存在性
python - <<'PY'
import json, re
from pathlib import Path
for run, task in [("pay_rules_dev","pay-normal-wechat"), ("D2_rules_dev","pay-timeout-fast")]:
    p = Path("runs")/run/task/"trace.jsonl"
    for r in [json.loads(l) for l in p.read_text(encoding="utf-8").splitlines()][:6]:
        obs = r.get("obs") or ""
        btn = re.search(r"确认支付' @(\d+),(\d+)-", obs)
        print(run, f"s{r['step']}", "确认支付" in obs, btn.group(2) if btn else "-")
PY
```
