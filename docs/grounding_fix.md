# 重大修复：动作落地层「同文案取第一个」把视觉门控题判废了

## 一句话

模型给出了**正确坐标**，harness 却因为 `node_text` 匹配优先而**丢弃坐标、点了第一个同文案控件**。
凡是"多个控件文案完全相同、只能靠颜色/位置区分"的题（colorgate 家族），
在此修复前**对任何模型都不可解**——测出来的是 harness 的行为，不是模型的能力。

## 铁证（真机 D4，支付视觉门控）

`runs/D4_qwen38vision_dev/pay-colorgate` 第 2 步的原始动作与执行日志：

```json
action: {"action":"click","x":628,"y":1127,"node_text":"微信支付",
         "reason":"协议已勾选，点击下方的绿色微信支付按钮（正规入口）拉起支付弹窗"}
exec  : click_node(微信支付)      ← 坐标被丢弃，按文案点了第一个（上方红色假冒入口）
```

对照文本模型同一题：

```json
action: {"action":"click","x":628,"y":896,"node_text":"微信支付",
         "reason":"点击第一个微信支付按钮（假设为绿色正规入口）"}
exec  : click_node(微信支付)      ← 同样被覆盖
```

两者的 `exec` 完全相同：**y=1127（下方绿）与 y=896（上方红）落地成了同一次点击**。
视觉模型的判断（"下方的绿色"）是对的，却被落地层抹掉了。

## 旧逻辑（错在哪）

```python
if action.get("node_text"):
    n = find_node_by_text(nodes, action["node_text"])   # 取第一个匹配（优先 clickable）
    if n:
        device.click_node(n)          # ← 模型给的 x,y 永远轮不到
        return ...
x, y = resolve_action_pos(action, nodes)
device.click(x, y)
```

`find_node_by_text` 在多匹配时静默返回第一个，**既不报错也不反馈**。

## 新逻辑（三条）

1. **坐标优先**：动作里带 `x,y` 就按坐标落地（模型的显式意图不可被文案匹配覆盖）；
2. **歧义拒绝执行**：只有 `node_text`、且它匹配到 **多个**可点击控件时 → 不点击，
   返回 `AMBIGUOUS:n`；
3. **歧义反馈闭环**：下一步观测里注入系统提示，告知"上一步未执行、树里有 n 个同文案控件，
   请结合截图选出目标并给出 bounds 几何中心坐标"；`NOOP` 同理提示补坐标。

同时把提示词里那条**帮凶规则**反转了：

| | 旧提示 | 新提示 |
|---|---|---|
| 定位方式 | "优先用 node_text 指认文本（比坐标更可靠），坐标仅作备选" | "**必须以 x,y 坐标为准**；node_text 只作核对。同文案多控件时务必结合截图判断并给坐标，只写文案会被判歧义且不执行" |

`ACTION_SCHEMA` 里 `x/y` 也从"click 用，与 y 成对"改为"**click 必填**：目标控件 bounds 的几何中心"。

## 对历史成绩的追溯性影响（诚实声明）

| 受影响结论 | 修复前含义 | 修复后含义 |
|---|---|---|
| 登录域 `colorgate`「文本智能体 ≈50% 胜率」 | 实际是 harness 取第一个匹配 + 变体按种子洗牌位置 → 50% | 才真正是"模型靠位置猜"的 50% |
| 视觉模型 colorgate「6 步 / 1 步通过」 | 可能是 harness 恰好替它点对 | 需以修复后重测为准 |
| 支付域 `pay-colorgate/2` 真机 D4：文本 1/2、视觉 **1/2** | 视觉的 1/2 是**被冤枉的**（它判断正确） | 视觉应得 2/2（D6 正在复验） |

因此：**所有含同文案多控件的任务，其修复前成绩都应标注为"harness 限定成绩"**，
不可直接用于模型间横向比较。

## 连带揭发的第二个 bug：sim 三套坐标空间不一致（更严重）

坐标优先落地一上线，sim 上的视觉门控题立刻变成"连点三次毫无反应"。逐层取证后发现
**离线模拟器存在三个互相不一致的坐标空间**：

| 空间 | 尺寸 | 谁在用 |
|---|---|---|
| app 逻辑空间 | 1080×1920 | `SimApp.nodes()` 的 bounds、`SimApp.click()` 命中测试 |
| 截图 PNG 像素空间 | 720×1280 | `render_png()`（`scale = 720/1080`）、模型看到的图 |
| `SimDevice.click()` 入参假定空间 | 720×1280（rcanvas） | 会把入参 ×1.5 换算到 app 空间 |

而旧 `dump_tree()` **把 1080 空间的 bounds 原样公布给模型**。于是：

```
模型从树里读到绿按钮 (120,900-520,996) → 取中心 (320,948) → 发给 harness
SimDevice.click: 320×1080/720=480, 948×1920/1280=1422 → 落到 (480,1422)
按钮实际范围 y∈[900,996] → 点在按钮下方 → 永远点空
```

真机 D4 视觉模型轨迹里"同一坐标连点 3 次、页面毫无变化"就是这个症状。
旧的 `node_text` 优先落地恰好**绕过**了坐标换算（`click_node` 直接把 app 空间 bounds
喂给 `app.click`），所以这个 bug 一直没暴露——两个 bug 互相掩护。

### 修复：统一坐标契约

1. `dump_tree()` 公布的 bounds **缩放到截图像素空间**（720×1280），
   使「树里坐标」＝「图上位置」＝「模型该输出的坐标」；
2. `click_node()` 改为走 `click()`，统一做 render→app 换算，不再自行绕过。

### 三空间一致性验证（实测）

```
公布 bounds：绿 (80,600-346,664)　红 (360,600-640,664)
截图尺寸：(720, 1280)                      ← 与公布空间一致
绿按钮中心像素 = (34,170,85)  = #22AA55    ← 正是绿色
红按钮中心像素 = (238,68,68)  = #EE4444    ← 正是红色
click(213,632)（模型视角中心） → stage: privacy → done   命中 ✅
click_node(绿) → done ✅　click_node(红) → browse（仅浏览＝错误路径）✅
```
