# 鸿蒙 App 支付功能 Benchmark 设计（Payment Benchmark）

目标：**判断某个 App 的支付功能是否正常**——核心信号是"支付渠道能否成功拉起
第三方支付平台弹窗"。拉起层为页内 Mock（语义等价：点击渠道 → 出现该平台品牌
支付弹窗 = 拉起成功；真实 SDK 拉起留作真机扩展位）。

## 1. 支付渠道口径

| 渠道 key | 品牌弹窗特征（判定依据） |
|---|---|
| wechat | 弹窗标题含「微信支付」 + 金额 + 「确认支付」按钮 |
| alipay | 弹窗标题含「支付宝」 |
| bankcard | 弹窗标题含「银行卡支付」 |
| huawei | 弹窗标题含「华为支付」 |

## 2. 两类任务

### P-NORMAL：完成支付
前置（协议勾选/金额确认）→ 选择任一渠道 → **渠道弹窗拉起（milestone）** →
mock 支付密码(123456) → 确认 → 支付成功页。
指标：成功率 / 拉起成功率（首个渠道弹窗 milestone 达成占比）/ 步数 / token。

### P-DIAG：诊断异常支付
- B1 单渠道故障：点击该渠道显示明确错误提示（如「暂时无法拉起微信支付，请更换支付方式」），
  Agent 须换渠道并完成支付，trace 中记录"故障渠道识别"；
- B2 死弹窗：渠道弹窗拉起但无确认按钮，须返回重选；
- B3 空白页：拉起后空白页，须 Back 恢复；
- B4 全故障：所有渠道均不可用 → 正确终点是「暂无可用的支付方式」页（agent 应停止并 done）。
指标：判异常准确率（结论与 ground truth 渠道匹配）。

## 3. 判定

- `goal.success`：成功页/终点页谓词（welcome_marker 或「暂无可用的支付方式」）；
- `goal.milestones`：渠道弹窗特征谓词列表，runner 记录每步首个达成，用于拉起成功率；
- `goal.forbid`：误点取消支付/未勾选协议强点等。

## 4. 模板/模拟器

- 模板 `PaymentPage.ets`，槽位：`CHANNELS`(逗号子集)、`BROKEN`(故障渠道，逗号)、
  `AMOUNT`、`PAY_PWD`、`ERR_TEXT`、`DEAD_POPUP`、`BLANK_PAGE` 等；
- sim 镜像 `PaymentApp` 语义同构；broker 渠道点击 → 状态化错误提示（可判定）。

## 5. 指标汇总

| 指标 | 计算 |
|---|---|
| 支付完成率 | P-NORMAL 成功任务占比 |
| **渠道拉起成功率** | milestone 达成的任务尝试占比（分渠道） |
| 判异常准确率 | P-DIAG 结论匹配 ground truth 占比 |
| 换渠道恢复率 | B1 中成功换渠支付的任务占比 |
| **黑帧率** | 防截屏导致的无效截图步占比（`scorer` 的 `black_frames`） |

## 6. 二期形态（B5~B9，已实现并验证）

| 形态 | 机制 | 正确行为 | 判定锚点 |
|---|---|---|---|
| B5 拉起后取消 | 正常拉起微信 → 用户改主意 | 点「取消」→ 改选华为完成支付 | 两个渠道 milestone 均需命中 |
| B6 风控二次确认 | 输密码后弹「再次确认支付」 | 再次确认 | milestone `risk_twice` |
| B7 金额不一致 | 订单 ¥199 但弹窗 ¥1990 | **不得支付**，点「取消」 | `cancel_alert_marker` + forbid 支付成功 |
| B8a 限时支付 | 弹窗内 45s 倒计时 | 倒计时内完成支付 | forbid `timeout_marker` |
| B8b 放任超时 | 8s 倒计时 | **故意等待**至订单关闭 | `timeout_marker` + forbid 支付成功 |
| B9 退款闭环 | 支付成功后出现「申请退款」 | 支付 → 二次确认 → 申请退款 | `refund_marker` + milestone 链 |
| **B10 输入法裁剪按钮** | 弹窗位置过低（`POPUP_MARGIN=320vp`），软键盘弹出后「确认支付」被裁出组件树 | **按返回键收起键盘** → 按钮回到树里 → 点确认 | 支付成功页；milestone `alipay` |

> B10 来自真机实测发现的**平台级布局陷阱**（裁剪阈值实测在 y≈1411 存活 / y≈1513 被裁之间），
> 完整证据链见 `docs/ime_clip_finding.md`。为避免其余支付题被同一缺陷不公平地判负，
> 所有非 B10 变体的 `POPUP_MARGIN` 统一设为 **60vp**（键盘安全）。

## 6b. 支付域视觉门控（P-VISUAL）

支付页也应有"只能看图才能做对"的题，用于检验视觉能力在支付场景的价值
（考点刻意放在**密码输入之前**，避开防截屏黑帧区）：

| 变体 | 机制 | 文本智能体期望 | 视觉智能体期望 |
|---|---|---|---|
| `pay-colorgate` | 两个文字完全相同的「微信支付」按钮，**红色为假冒入口（点击即拦截判负）**、绿色为正规入口；假冒在前 | ~50%（只能靠位置猜） | 100% |
| `pay-colorgate2` | 同上，**顺序反转**（正规在前） | ~50% | 100% |

配套的两条完整性约束（已实测验证）：

1. **颜色不得泄漏进组件树**：sim 端 `SimDevice.dump_tree()` 主动剥离 `color` 字段，
   真机端 `flatten_nodes()` 故意不提取 `backgroundColor`（dumpLayout 原始输出里是有的）；
   实测观测文本中不含任何色值，两个按钮的观测行完全同构（仅 bounds 不同）；
2. **位置不得携带信息**：成对反序变体使"永远点第一个/第二个"的猜测策略在套件层面收敛到 50%。

规则基线在这两题上**按设计诚实弃权**（命中"视觉门控任务：规则基线无颜色/图形感知"分支，
主动等待至步数耗尽），与登录域 colorgate 的处理一致。

模板 `PaymentPage.ets` v2 支持全部形态（含 `onBackPress` 返回语义、倒计时定时器、
按渠道粒度的 `BROKEN_JSON/DEAD_JSON/BLANK_JSON` 故障清单）；sim 镜像 `PaymentApp` 同构。
规则基线在 14 个精选支付任务上 **14/14**、矩阵生成的 14 个随机支付变体上 **14/14**。

## 7. 平台约束：支付密码页防截屏（必读）

真机实测：支付弹窗（含 `InputType.Password`）出现后，`uitest screenCap` 返回的 PNG
**99.6% 像素为黑、灰度均值 0.5**（系统防截屏，等价 Android `FLAG_SECURE`），
而 UI 树不受影响。详见 `docs/blackscreen_finding.md`。

因此本 Benchmark 的硬性口径：

1. 支付类任务的判定**必须以 UI 树 + milestone 为准**，不得依赖截图；
2. harness 已内置黑帧检测（均值≤8 或暗像素≥98%）→ 自动丢弃图像、降级为纯树观测并提示模型；
3. 报告须同时给出**黑帧率**，否则会把平台限制造成的失败误记为模型缺陷；
4. 若要考察视觉能力，考点应放在密码输入之前（渠道图标识别、金额核对、风控弹窗判读）。

## 8. 顶层交付：支付功能健康判定书

`scripts/pay_verdict.py` 把一次 run 汇成**双侧判定**：

- **应用侧**（回答"这个 App 的支付功能正常吗"）：NORMAL / PARTIAL / DEGRADED / BROKEN，
  依据 = 四渠道拉起率 + 正常流程完成率；
- **Agent 侧**（回答"这套 Agent 能当支付体检员吗"）：胜任 / 部分胜任 / 不胜任，
  依据 = 注入故障识别率 + 恢复完成率。

实测（真机）：四路 run 的应用侧判定均为 **NORMAL（四渠道拉起 100%）**；
Agent 侧 qwen3.7-max 与 qwen3.8-max 判为**胜任**（识别 100%、成功率 100%），
glm-5.3-flash 为**部分胜任**（识别 100% 但恢复率 75%），规则基线**不胜任**（识别 50%）。
输出：`docs/pay_verdict.md` + 每个 run 目录下的 `verdict.json`。
